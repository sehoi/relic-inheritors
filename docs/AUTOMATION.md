# 자율 개발 루프 설계 (Loop Engineering)

목표: **사용자가 자는 동안에도 게임이 계속 만들어지고, 아침에 와서 훑어보면 진행 상황이 파악되는 것.**

## 1. 전체 그림

```
                 ┌──────────────────────────────────────────────┐
                 │             docs/GDD.md (기획서)              │
                 │            = 무엇을 만들지의 근거              │
                 └───────────────────┬──────────────────────────┘
                                     │ 백로그가 3개 미만이면 여기서 보충
                                     ▼
   ┌───────────────────────── docs/BACKLOG.md ─────────────────────────┐
   │  - [ ] T-014  전투: 상태이상 '독' 구현                             │
   │  - [ ] T-015  UI: 아이템 사용 메뉴                                 │
   └───────────────────────────┬───────────────────────────────────────┘
                               │  1회 이터레이션 = 태스크 1개
                               ▼
   /loop /next-task  ──▶  ① 브랜치  ② 테스트 먼저  ③ 구현
                          ④ npm run verify        (❌ → 수정, 2회 실패 시 BLOCKED)
                          ⑤ 브라우저 스모크 + 스크린샷
                          ⑥ commit → push → gh pr create
                          ⑦ /code-review 셀프 리뷰 → 지적사항 반영
                          ⑧ CI 초록 확인 → squash merge
                          ⑨ BACKLOG 체크 + PROGRESS.md 1줄 기록
                               │
                               └──▶ 다음 이터레이션 (반복)
```

## 2. 이터레이션의 정의

**1 이터레이션 = 백로그 태스크 1개 = PR 1개.**

태스크는 "한 번에 끝낼 수 있는 크기"로만 백로그에 들어간다. 판단 기준:
- 변경 파일 20개 이하, 추가 라인 500줄 이하로 끝날 것
- 완료 조건(Definition of Done)이 자동으로 검증 가능할 것
- 안 되면 → 태스크를 쪼개서 백로그에 다시 넣는다

## 3. 구동 방법

```bash
/loop /next-task
```

`/loop`에 인터벌을 주지 않으면 모델이 스스로 페이스를 정한다(작업이 끝나는 대로 다음 이터레이션). 게임 개발처럼 **각 이터레이션 길이가 들쭉날쭉한 작업에는 고정 인터벌보다 self-paced가 맞다.**

정지: `/loop` 중단 또는 루프가 스스로 정지 조건(§5)에 걸릴 때.

## 4. `.claude/commands/next-task.md` — 이터레이션 절차

슬래시 커맨드 안에 절차를 못 박아 두면, 매 이터레이션이 같은 규율로 실행된다. 담을 내용:

```
0.  git checkout main && git pull --ff-only
1.  docs/BACKLOG.md 최상단 미완료 태스크를 하나 고른다.
    - 백로그가 3개 미만이면 GDD.md를 읽고 다음 태스크 5개를 먼저 추가한다.
    - BLOCKED 표시된 태스크는 건너뛴다.
2.  git checkout -b feat/<태스크ID>-<슬러그>
3.  실패하는 테스트를 먼저 쓴다 (core 로직인 경우 필수).
4.  구현한다.
5.  npm run verify  → 실패하면 고친다. 같은 태스크에서 2회 연속 실패하면
    BACKLOG에 BLOCKED 사유를 적고 이 이터레이션을 중단, 다음 태스크로.
6.  dev 서버를 띄우고 내장 브라우저로 부팅 확인:
    - 콘솔 에러 0
    - 스크린샷을 docs/screenshots/<태스크ID>.png 로 저장
7.  커밋 (Conventional Commits) → push → gh pr create
    PR 본문: 무엇을/왜, 검증 방법, 스크린샷, 남은 리스크
8.  /code-review 로 셀프 리뷰. 지적된 것 중 실제 문제만 수정 후 push.
9.  gh pr checks 로 CI 초록 확인 → gh pr merge --squash --delete-branch
10. docs/BACKLOG.md 체크박스 갱신 + docs/PROGRESS.md 에 1~3줄 기록
    (날짜, 태스크ID, 한 일, 알게 된 것, 다음에 걸릴 것 같은 것) → main에 push
```

## 5. 가드레일 — 폭주를 막는 장치

자율 루프에서 실제로 사고가 나는 지점들만 골라 막는다.

### 하지 않을 것 (하드 금지)
- `main`에 직접 커밋/푸시 (병합은 PR 경유만)
- `git push --force`, `git rebase`, `git reset --hard`, 히스토리 재작성
- 브랜치/태그 삭제 (자기 feature 브랜치 머지 후 삭제는 예외)
- `npm run verify` 실패 상태에서 커밋
- CI가 빨간 PR을 머지
- 시크릿·토큰을 코드나 커밋 메시지에 기록
- 사용자에게 확인 없이 새로운 유료 서비스·외부 API 연동

### 정지 조건 (루프가 스스로 멈추고 사용자를 호출)
| 조건 | 이유 |
|---|---|
| 3개 태스크 연속 BLOCKED | 설계가 막혔거나 백로그가 잘못 쪼개져 있다 |
| `npm run verify`가 main에서 실패 | 기반이 깨졌다. 진행할수록 손해 |
| 같은 파일을 5 이터레이션 연속 수정 | 헛돌고 있다는 신호 |
| 아키텍처 경계 변경이 필요 (core↔game 의존 방향 등) | 사람 판단이 필요한 급 |
| 런타임 의존성 신규 추가 | 되돌리기 비싸다. PR 본문에 사유 필수 + 사용자 확인 |

### 자유롭게 해도 되는 것
- 콘텐츠 추가 (몬스터, 아이템, 스킬, 대사, 맵)
- 밸런스 수치 조정 (시뮬 테스트가 지켜준다)
- 리팩터링 (테스트가 초록인 한)
- 백로그 태스크 생성·순서 조정

## 6. 진행 상황 가시성 — 사람이 아침에 확인하는 법

개입 없이 돌린다는 건 **나중에 몰아서 확인한다**는 뜻이다. 그래서 확인 비용을 낮추는 게 설계의 일부다.

| 확인처 | 내용 | 걸리는 시간 |
|---|---|---|
| `docs/PROGRESS.md` | 이터레이션별 1~3줄 저널. 위에서부터 읽으면 밤새 뭐 했는지 파악 | 1분 |
| GitHub PR 목록 | 각 PR = 하나의 변경 단위, 스크린샷 포함 | 3분 |
| `docs/screenshots/` | 화면이 실제로 어떻게 변했는지 | 1분 |
| `npm run dev` | 직접 플레이 | — |
| `docs/DECISIONS.md` | 루프가 내린 아키텍처 판단과 근거 | 필요 시 |

### 완성도 계산

루프는 이터레이션마다 완성도를 보고한다. **매번 감으로 답하면 숫자가 들쭉날쭉해져 아무 의미가 없으므로** 가중치를 고정한다.

| 마일스톤 | 가중치 | 근거 |
|---|---:|---|
| M0 부트스트랩 | 5% | 필수지만 플레이 분량은 0 |
| M1 탐색 | 10% | 이동·대화·맵 전환 |
| M2 전투 코어 | 20% | 턴제 상태 머신, 시뮬레이터 |
| **M3 유물 시스템** | **25%** | 이 게임의 중심. 장착·공명·숙련·침식 + 밸런스 불변식 |
| M4 거점·저장 | 15% | 정화소·상점·메뉴 UI·세이브 |
| M5 수직 슬라이스 | 15% | 콘텐츠 채우기. 40분 플레이 |
| M6 폴리시 | 10% | 오디오·연출·밸런스 패스 |

각 마일스톤 안에서는 완료 태스크 비율로 부분 점수를 준다.
예: M1의 8개 태스크 중 5개 완료 → `10% × 5/8 = 6.3%`

**백로그 항목 수는 완성도가 아니다.** 인프라 작업은 항목 수를 빠르게 올리지만 플레이 가능한 분량은 늘리지 않는다. 보고할 때 이 점을 흐리지 않는다.

## 7. 리뷰 체계 — 2단

1. **루프 내부 셀프 리뷰** — 매 PR에서 `/code-review` 실행. 즉각적이고 무료에 가깝다.
2. **(선택) GitHub Actions PR 리뷰** — 저장소 시크릿에 `ANTHROPIC_API_KEY`를 넣고 Claude Code Action을 붙이면, PR마다 독립적인 리뷰가 한 번 더 돈다. 셀프 리뷰는 "자기 코드를 자기가 보는" 한계가 있어서, 자율성이 길어질수록 이 2단이 값을 한다.
   - 비용이 발생하므로 **기본은 꺼두고**, 루프를 장시간 돌릴 때 켜는 것을 권장.

## 8. 대안으로 고려했다가 택하지 않은 것

| 대안 | 왜 안 골랐나 |
|---|---|
| GitHub Issues를 백로그로 사용 | 매 이터레이션마다 API 왕복이 늘고, 로컬 파일보다 루프가 읽기 비싸다. 파일이면 diff로 진행이 남는다. 나중에 규모가 커지면 전환 검토. |
| 고정 인터벌 `/loop 30m` | 이터레이션 길이가 불균일해서 겹치거나 놀거나 한다. self-paced가 맞다. |
| 여러 에이전트 병렬 개발 | 게임은 시스템 간 결합이 강해서 병렬 PR이 충돌한다. 초기엔 직렬이 훨씬 빠르다. |
| 사람 승인 후 머지 | 개입 없는 진행이라는 요구와 정면으로 충돌. 대신 CI + 셀프 리뷰 + 되돌리기 쉬운 squash 머지로 대체. |
