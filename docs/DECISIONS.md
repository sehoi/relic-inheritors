# 아키텍처 결정 기록 (ADR)

되돌리기 비싼 판단만 기록한다. 사소한 구현 선택은 여기 쓰지 않는다.
루프가 **경계를 바꿔야 한다고 판단하면, 바꾸지 말고 여기에 문제를 적고 멈춘다.**

형식:

```md
## ADR-00N · <제목>
- 날짜 / 상태: 채택 | 대체됨 | 보류(사용자 판단 필요)
- 맥락:
- 결정:
- 결과 및 트레이드오프:
```

## ADR-001 · core 레이어에 Phaser 의존성을 금지한다
- 2026-08-04 / 채택
- 맥락: 자율 루프는 자동 검증 신호가 없으면 동작할 수 없다. 게임 로직이 엔진에 결합되면 헤드리스 테스트가 불가능해진다.
- 결정: `src/core/**`는 순수 TypeScript로 유지하고 `phaser` import를 ESLint로 금지한다. 렌더링은 `src/game/**`에서만.
- 결과: 코드가 한 겹 늘어나고 어댑터가 필요하다. 대신 전투·성장·세이브 로직 전체가 1초 내 테스트 가능해진다. 자율 개발의 전제 조건이므로 비용을 감수한다.

## ADR-002 · 모든 무작위성은 시드 RNG를 경유한다
- 2026-08-04 / 채택
- 맥락: 재현 불가능한 버그는 자율 루프가 수정할 수 없다. 밸런스 검증도 결정론 없이는 성립하지 않는다.
- 결정: `Math.random()` 직접 호출 금지. `core/rng`의 시드 기반 RNG만 사용하고, 전투 로그에 시드를 남긴다.
- 결과: RNG 상태를 명시적으로 넘겨야 해서 함수 시그니처가 길어진다. 대신 버그가 회귀 테스트로 즉시 전환되고, 헤드리스 밸런스 시뮬레이션이 가능해진다.

## ADR-003 · 백로그를 GitHub Issues가 아닌 저장소 파일로 둔다

## ADR-004 · 능력의 출처를 캐릭터가 아닌 유물에 둔다
- 2026-08-04 / 채택
- 맥락: 자율 루프가 콘텐츠를 늘릴 때 게임이 실제로 깊어져야 한다. 캐릭터에 스킬이 귀속된 통상 구조에서는 콘텐츠 추가가 선형 증가에 그치고, 새 캐릭터 추가는 시스템·UI·서사 변경을 동반해 루프가 감당하기 어렵다.
- 결정: 캐릭터 고유 스킬을 1~2개로 제한하고, 능력의 대부분을 유물(Relic)에서 공급한다. 유물은 파티 8슬롯에 자유 배분되며, 태그 조합으로 공명(Resonance)이 성립한다.
- 결과: 유물 1개 추가가 조합 공간을 곱으로 늘린다. `data/relics.ts`만 건드리면 되므로 루프가 안전하게 확장할 수 있다. 대신 밸런스가 조합 폭발로 인해 사람 눈으로 검증 불가능해지므로, ADR-005의 자동 불변식 검증이 반드시 함께 성립해야 한다. 둘은 한 쌍이다.

## ADR-005 · 밸런스를 시뮬레이션 불변식으로 검증한다
- 2026-08-04 / 채택
- 맥락: ADR-004로 조합 공간이 폭발한다. 자율 루프가 밸런스를 망가뜨렸는지 사람 없이 판정할 수단이 필요하다.
- 결정: `tools/sim.ts`로 조합별 전투를 헤드리스 반복 실행하고, GDD §5.5의 불변식(지배 전략 부재, 유효 조합 다양성, 침식 압박 실재, 사장된 유물 부재, 전투 길이 범위)을 테스트로 강제한다. 위반 시 `npm run verify` 실패.
- 결과: 밸런스 튜닝이 루프가 자율적으로 수행 가능한 작업이 된다. 대신 시뮬 실행 시간이 CI에 얹히고, 불변식 임계값 자체가 잘못 잡히면 잘못된 방향으로 수렴할 위험이 있다 — 임계값은 `data`에 두고 M5 이후 사람이 한 번 재검토한다.

## ADR-006 · 에셋은 사전 등재된 것만 사용한다
- 2026-08-04 / 채택
- 맥락: 루프는 그림을 그릴 수 없고, 인터넷에서 임의로 내려받게 두면 라이선스 오염과 존재하지 않는 경로 참조가 발생한다.
- 결정: `assets/index.json`에 등재된 에셋만 사용한다. 없으면 단색 도형 플레이스홀더를 쓰고 백로그에 "에셋 필요" 항목을 남긴다. 출처·라이선스는 `assets/CREDITS.md`에 기록하며 누락 시 CI가 실패한다.
- 결과: 에셋 부재가 루프를 멈추지 않는다(플레이스홀더로 진행). 대신 화면 완성도는 사람이 에셋을 보충해줄 때까지 올라가지 않는다 — 의도된 트레이드오프다.

## ADR-007 · 제3자 에셋 팩은 디렉터리 단위로 선언한다 (벤더 팩)
- 2026-08-04 / 채택 · ADR-006을 보완함
- 맥락: ADR-006은 `assets/` 아래 모든 파일의 개별 등재를 요구했다. 그런데 실제 제3자 팩은 수백 개 파일로 온다 — Kenney Tiny Town + Tiny Dungeon 을 들이자 272개의 낱장 PNG 와 Tiled 템플릿, 라이선스 파일이 한꺼번에 생겼다. 개별 등재는 비현실적이고, 그렇다고 고아 검사를 풀면 출처 불명 파일이 조용히 쌓이는 것을 막을 수 없다. 필요한 파일만 남기고 지우는 방안도 검토했으나 팩의 원형과 Tiled 템플릿을 잃는다.
- 결정: 색인에 `packs` 를 도입한다. 디렉터리 하나를 **출처·라이선스와 함께** 선언하면 그 안의 파일은 고아 검사에서 제외된다. 실제로 코드가 로드하는 파일은 그와 별개로 `entries` 에 등재하되, 팩 안의 항목은 `source` 를 생략하고 팩의 출처를 물려받는다.
- 결과: 보증("출처 불명 파일이 없다")이 유지된다 — 팩도 출처를 요구받기 때문이다. 중복 기재를 강제하지 않아 팩과 항목이 어긋날 여지도 없앴다. 대신 팩 내부의 개별 파일은 용도가 기록되지 않으므로, 실제로 쓰는 파일은 반드시 `entries` 에 올려야 한다는 규율이 필요하다. `assets` 전체를 팩으로 선언하는 것은 금지한다(고아 검사가 무력화된다). 팩 디렉터리 간 중첩도 금지한다(소유가 모호해진다).

## ADR-010 · 침식 임계를 최대 MP에 비례시키고, 고위력 스킬의 MP 비용을 가파르게 매긴다
- 2026-08-05 / 채택 · T-019 의 진단을 정정함
- 맥락: T-019 시뮬레이터가 보스전 승률 붕괴를 찾아냈다 — Lv5 99% → Lv20 44% → Lv40 39%. **당시 원인을 "침식 임계가 고정값이라 후반에 폭주가 누적된다"로 진단했는데, 이 진단은 틀렸다.**
- 정정: 변수를 분리해 재보니 폭주하던 쪽은 주로 **보스**였다. 임계를 최대 MP에 비례시키자 보스가 자멸하지 않게 되어 승률이 오히려 더 떨어졌다(Lv20 44%→32%, Lv40 39%→23%). 즉 **고정 임계가 고레벨 보스에 대한 의도치 않은 제동장치로 작동하고 있었다.**
- 실제 원인: 보스는 액터가 하나라 MP 가 곧 고위력 스킬의 시전 횟수다. 보스 MP 배수가 2였고 최고 위력 스킬(위력 220)의 비용이 9뿐이라, 레벨이 오를수록 시전 횟수가 늘어 실효 화력이 초선형으로 증가했다.
- 결정: 세 가지를 함께 바꾼다.
  1. 침식 임계 = `base + 최대MP × perMaxMp` (10 + 2.2). "MP 를 얼마나 쓰면 폭주하는가" 가 레벨과 무관해진다. 그 자체로 옳은 설계이며, 폭주를 밸런스 제동장치로 쓰는 것은 우연에 기대는 일이다.
  2. 보스 MP 배수 2 → 1. 보스에게 배의 MP 를 주면 그게 곧 배의 고위력 시전이 된다.
  3. `sundering-arc` MP 비용 9 → 14, 침식 34 → 40. 위력 220 은 기본의 2.2배인데 비용이 그에 못 미쳤다.
- 결과: 100% / 97.7% / 62.7% (Lv5/20/40). 붕괴가 사라지고 난이도 곡선이 남았다. GDD §5.5 에 **불변식 8(레벨 간 난이도 붕괴 부재, 승률 차이 45%p 이내)** 을 추가해 회귀를 막는다.
- **교훈**: 시뮬레이터가 "무엇이 잘못됐는지" 는 정확히 보여줬지만 "왜" 는 사람이 잘못 읽었다. 원인을 지목할 때는 변수를 분리해 재보고 말해야 한다. 이 프로젝트에서 밸런스 가설은 실측 전까지 가설일 뿐이다.

## ADR-009 · 데미지 공식에 관통 하한을 둔다
- 2026-08-05 / 채택 · GDD §6.2의 초기 공식을 수정함
- 맥락: 초기 공식은 순수 감산형(`max(1, ATK*p/100 - DEF/2)`)이었다. M2 착수 전에 실제 수치로 검증했다.
  - 스케일링은 건강했다. 레벨 1~40 전 구간에서 잡몹 5턴·보스 16턴으로 안정적이고, "1 데미지 바닥"은 정상 콘텐츠에서 도달하지 않는다(여유 +15 ~ +116). 비교로 돌린 비율형은 오히려 레벨이 오를수록 전투가 늘어졌다.
  - **문제는 유물 설계와의 충돌이었다.** ADR-004에 따라 유물 8슬롯이 스탯을 보정하는데, 감산형에서는 총 DEF가 적 ATK의 2배를 넘으면 받는 피해가 1로 고정된다. 필요한 값은 Lv5에서 슬롯당 +2.2, Lv20에서 +6.1 — 유물 설계에서 평범한 수치다. 그 조합을 찾는 순간 무적이 되고, ADR-005의 "지배 전략 부재" 불변식이 구조적으로 깨진다.
  - 감산형은 스탯 보정을 증폭하기도 한다(ATK +50% → 데미지 +75%). 스택 수익이 초선형이라 특정 축에 몰아주는 것이 항상 유리해진다.
- 결정: 감산형을 유지하되 **관통 하한**을 둔다 — `max(raw * PIERCE, raw - DEF * DEF_FACTOR, 1)`, `PIERCE = 0.2`. 치명타 배율은 2.0에서 **1.5**로 낮춘다.
- 대안 검토: 비율형(`raw * K/(K+DEF)`) 전환은 조합 격차를 더 줄였지만(1.05배 vs 1.60배) 전투 길이 드리프트를 낳고 밸런스 전체를 다시 잡아야 한다. 얻는 것 대비 비용이 컸다.
- 결과: 무적이 사라지고(방어 감소 상한 65%), 전투 길이는 유지되며(잡몹 4~5턴·보스 11~16턴), 고전 JRPG의 "방어력 높은 적은 딱딱하다"는 감각도 남는다. 무작위 폭은 2.4배 → 1.65배로 줄어 조합 설계의 비중이 커진다.
- **한계**: 검증에 쓴 "조합 격차" 지표는 힐·스킬·다수 적 없이 `생존턴 × 딜` 로 계산한 거친 근사다. 방향성은 신뢰하되 숫자 자체는 신뢰하지 않는다. 실제 판정은 M3의 시뮬레이터(ADR-005)가 한다 — 이 공식은 그 위에서 다시 측정된다. 스탯 성장 곡선도 미확정이라 선형을 가정했다.

## ADR-008 · Zod 대신 자체 검증 커널을 쓴다
- 2026-08-05 / 채택 · GDD와 ARCHITECTURE의 "Zod" 명시를 대체함
- 맥락: 설계 초기에 데이터 검증 도구로 Zod를 적었다. 그 사이 네 곳(에셋 색인 310줄, 타일맵 318줄, 대화, 포탈)에 손으로 쓴 검증기가 생겼고, 이들이 실제로 잡는 것의 상당수는 **Zod가 표현할 수 없는 교차 규칙**이었다 — 어떤 타일셋에도 속하지 않는 gid, collision 레이어 누락, 도착 지점이 반대편 포탈 위인 경우. Zod를 도입해도 이 규칙들은 그대로 손으로 써야 하고, 얻는 것은 형태 검사뿐이다.
- 또한 CLAUDE.md 규칙 8이 런타임 의존성 추가에 사용자 승인을 요구한다. 승인을 기다리며 M1을 멈추는 것보다, 실제로 필요한 것이 무엇인지 먼저 확인하는 편이 낫다고 판단했다.
- 결정: Zod를 도입하지 않는다. 대신 네 검증기가 공유하던 뼈대를 `core/validation` 으로 뽑는다 — 문제를 전부 모아 보고하는 수집기, 경로 접두사(`scope`), 읽기 도우미, 중복 검사기. ID로 참조되는 데이터는 `core/data/registry` 가 키·id 일치와 교차 참조를 맡는다.
- 결과: 런타임 의존성이 0으로 유지되고, **에러 메시지가 도메인 언어로 남는다** — 이 메시지는 사람보다 루프가 더 자주 읽으므로 중요하다. 대신 스키마가 크게 늘어나면(M3의 유물·스킬·아이템·적) 형태 검사 코드가 Zod보다 장황해진다. 그 시점에 재검토하되, 재검토의 기준은 "타이핑이 귀찮은가"가 아니라 **"검증기가 잡지 못하는 실수가 실제로 나오는가"** 로 한다.
- 이번에는 대화·포탈만 커널로 옮겼다. 에셋 색인과 타일맵은 메시지에 위치 접두사가 손으로 박혀 있어 옮기면 문자열이 바뀌고 테스트가 깨진다. **다음에 그 파일을 손댈 때 함께 옮긴다.**
